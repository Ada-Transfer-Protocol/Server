# AdaTP Reliability Model

**Audience:** operators and integrators. Companion to
[docs/spec/02-architecture.md](../spec/02-architecture.md); the limits
described here are implemented in the v1 server.

---

## 1. Delivery semantics — the contract

| Property | Guarantee |
| :-- | :-- |
| Delivery | **At-most-once.** A routable packet reaches each current room member zero or one times. No retransmission, no acknowledgements. |
| Ordering | **Per-sender only.** Packets from one connection arrive in send order (WebSocket/TCP ordering, single routing hop). Across different senders there is no global order. |
| Persistence | **None.** Nothing is stored; a packet not delivered live is gone. No offline delivery, no history replay for late joiners. |
| Duplicates | Not generated by the server. |
| Membership races | Broadcast targets are the members at routing time; a client mid-join may miss packets sent during the transition. |

Design consequence: applications needing acknowledgement build it in-band
(e.g. the reserved `FileAck`, or application-level receipts), and
late-join state recovery is an application convention
([GameState §3.3](../spec/07-media-game.md)).

## 2. Enforced limits

| Limit | Default | Config | On violation |
| :-- | :-- | :-- | :-- |
| Max payload size | 1 MiB | `MAX_FRAME_BYTES` | connection closed (`frame_too_large`) |
| WebSocket message cap | `MAX_FRAME_BYTES` + slack | derived | rejected at the WS layer |
| Idle timeout | 90 s without any inbound bytes | `IDLE_TIMEOUT_SECS` | connection closed (`idle_timeout`) |
| Keep-alive probing | WS protocol ping every 30 s | fixed | keeps NATs open; pong counts as activity |
| Auth failures | 3 per connection | fixed | closed (`auth_failed`) |
| Pre-auth violations | 10 per connection | fixed | closed (`preauth_flood`) |
| Outbound queue per connection | 256 messages | fixed | overflow **drops** the message for that receiver and increments `dropped_messages` |

## 3. Backpressure policy: drop, don't stall

Fan-out uses bounded per-connection queues. When a receiver is too slow
(saturated link, frozen tab), new messages for **that receiver only** are
dropped and counted — the sender, the room, and other receivers are
unaffected.

Rationale: AdaTP's core workloads (voice frames, game state, presence)
prefer fresh data over complete data; blocking a room on its slowest
member would convert one bad consumer into a room-wide outage, and
unbounded buffering converts it into a memory leak.

Operational signal: the `dropped_messages` counter in `/api/metrics`.
A non-zero, growing value means some client cannot keep up (or a room's
aggregate traffic exceeds a member's downlink).

## 4. Controlled close paths

Every termination is deliberate and logged with a reason
([error registry §3](../spec/appendix-error-codes.md)):

- **Client-initiated:** `Disconnect` packet (`client_disconnect`) or WS
  close (`peer_closed`).
- **Protocol violations:** malformed/oversized/undecryptable traffic —
  immediate close; violations never route.
- **Liveness:** `idle_timeout` after 90 s of silence despite pings.
- **Server shutdown/drain:** on SIGINT/SIGTERM the server sends every
  connection `Disconnect` (`server_shutdown`), waits briefly for flushes,
  then exits. Clients see an orderly goodbye, not a reset.

On every close the server unregisters the connection and announces
`PresenceUpdate "LEAVE"` to its room, so rosters converge.

## 5. State model and restart behaviour

The v1 server is a **single node** holding all state in memory:

- Connections, rooms, and session keys — in-process; lost on restart.
- SQLite — control-plane API keys only; survives restarts.
- After a restart every client must reconnect, re-handshake,
  re-authenticate, and re-join; rooms repopulate organically. SDKs SHOULD
  implement reconnect-with-backoff (reference SDKs currently surface
  disconnect events to the application rather than auto-reconnecting).

There is no clustering, room federation, or shared-nothing scale-out in
v1. Horizontal strategies (LB session pinning per room, one server per
shard) are deployment-level concerns documented in the production portal;
the protocol itself is silent about them.

## 6. Health and observability

- `GET /healthz` — process liveness (always 200 while serving).
- `GET /readyz` — readiness: verifies the database is reachable; 503
  otherwise.
- `GET /api/metrics` (x-api-key) — uptime, active connections, byte
  counters, per-room member counts, `dropped_messages`.
- Structured logs — one line per connection close including the reason
  slug and username, plus auth failures with peer address.

## 7. Honest non-claims

To prevent this document being quoted beyond its meaning:

- **Not** an exactly-once or guaranteed-delivery messaging system — use a
  broker with persistence if you need that.
- **Not** highly available in v1 — one process, in-memory state, restart
  drops all sessions.
- **No SLA implied** by anything in this repository; badge-style uptime
  claims are marketing, not engineering, and are avoided in v1 docs.
- **Not certified** for safety-critical, life-support, flight, or
  regulated medical/industrial control use. AdaTP has had no formal
  verification, no certification audit, and its testing is the public
  suite in `tests/`.
- Voice quality under loss/jitter degrades exactly as raw PCM over TCP
  degrades: head-of-line blocking on the WebSocket's TCP stream can add
  latency bursts; there is no FEC, no jitter buffer beyond what clients
  implement.
